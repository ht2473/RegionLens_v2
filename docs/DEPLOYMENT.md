# Развёртывание RegionLens

Установка системы на виртуальный сервер в контейнерах Docker Compose. Исходный код
на сервер не попадает: образ приложения собирается на машине разработчика и передаётся
по SSH (раздел 3).

---

## 1. Требования к серверу

| Параметр | Минимум | Рекомендуется |
|---|---|---|
| Процессор | 2 ядра | 4 ядра |
| Оперативная память | 4 ГБ | 8 ГБ |
| Диск | 20 ГБ SSD | 40 ГБ SSD |
| Операционная система | Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |
| Доменное имя | не обязательно | обязательно для сертификата и почты |

Служб пять (`docker/compose.prod.yml`):

| Служба | Назначение | Предел памяти |
|---|---|---|
| `caddy` | обратный прокси, сертификаты, статика, журнал обращений; принимает тело запроса целиком до передачи приложению | 512 МБ |
| `web` | приложение (gunicorn: процессов — `WEB_CONCURRENCY`, по числу ядер, в каждом 4 потока), сборка склада, начатая из панели, сбор источников и статистика посещений по таймерам хоста, маленькие таблицы пользователей и чтение PDF | 3,5 ГБ |
| `userdata-worker` | разбор и сборка больших таблиц пользователей по заявкам сайта, не больше двух сразу | 1,5 ГБ |
| `postgres` | PostgreSQL 18: учётные записи, справочники, сохранённое, обращения | 1 ГБ |
| `valkey` | Valkey 8: кэш и счётчики ограничителей | 192 МБ |

Предел не резервирует память, а не даёт одной службе вытеснить остальные. Замер
на стенде с рабочими настройками (10.11.2026): в обычной работе, в том числе под нагрузкой
сканера в тысячи запросов в минуту, — 1,4–1,7 ГБ на все службы; сборка склада одновременно
с разбором двух таблиц по 200 МБ — 2,8 ГБ (сайт 2,2 ГБ, служба разборов 0,6 ГБ). DuckDB в веб-процессе ограничен 256 МБ на процесс, сборка — 1 ГБ. Большие таблицы пользователей разбираются
в своём контейнере: нехватка памяти обрывает разбор, а не сайт. Пределы рассчитаны на VPS
с 8 ГБ.

Письма уходят сразу, а сборку, начатую из панели, приложение запускает отдельным процессом команды
`etl_build --run` в своём же контейнере. Одновременно идёт не больше одной сборки:
её охраняет рекомендательная блокировка PostgreSQL, которую берёт и команда `etl_build`.

Valkey хранит только кэш и счётчики: при нехватке памяти (128 МБ) вытесняются давно
не читанные ключи (`allkeys-lru`), на диск ничего не пишется.

Диск: образ около 1,4 ГБ (и по одному прежнему на откат), аналитический склад около
90 МБ, база данных — десятки мегабайт, загруженные наборы — по 10 МБ (хранятся три
последних), архив выпусков источников — около 0,3 ГБ в год, журнал Caddy — до 200 МБ
за 30 суток, резервные копии за 14 суток — до полутора гигабайт.

## 2. Подготовка сервера

```bash
sudo apt update && sudo apt upgrade -y
```

```bash
sudo apt install -y ca-certificates curl rclone
```

Docker — по официальному сценарию установки:

```bash
curl -fsSL https://get.docker.com | sudo sh
```

Стенд работает от отдельного пользователя `regionlens` из группы docker; от него же
выполняются выкладка (по ключу SSH) и таймеры:

```bash
sudo adduser --disabled-password --gecos "" regionlens && sudo usermod -aG docker regionlens
```

```bash
sudo mkdir -p /srv/regionlens && sudo chown regionlens:regionlens /srv/regionlens
```

Открытый ключ разработчика — в `/home/regionlens/.ssh/authorized_keys`. Межсетевой
экран открывает SSH и порты 80 и 443 (443 — и по UDP, для HTTP/3):

```bash
sudo ufw allow OpenSSH && sudo ufw allow 80/tcp && sudo ufw allow 443 && sudo ufw enable
```

Порты, опубликованные Docker, экран `ufw` не закрывает; у стенда опубликованы только 80
и 443, база и Valkey наружу не выходят.

**Вход по SSH — только по ключу.** Пользователь `regionlens` состоит в группе docker,
а это права администратора сервера, поэтому пароли и вход под root выключаются. Файл
`/etc/ssh/sshd_config.d/10-regionlens.conf`:

```
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
AllowUsers АДМИНИСТРАТОР regionlens
```

```bash
sudo sshd -t && sudo systemctl reload ssh
```

Новый вход проверяется во втором окне, пока первое открыто. Подбор по SSH отсекает
fail2ban (правило `sshd` включено сразу после установки):

```bash
sudo apt install -y fail2ban unattended-upgrades
```

```bash
sudo dpkg-reconfigure -plow unattended-upgrades
```

Вторая команда включает установку обновлений безопасности системы без участия человека.
Образы служб обновляет выкладка (раздел 3).

**Подкачка.** На сервере с 4 ГБ сборка склада вместе с разбором большой таблицы подходит
к пределу памяти. Файл подкачки в 2 ГБ даёт запас: ядро не остановит службу при коротком
всплеске.

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile
```

```bash
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

**IPv6.** Пределы частоты считаются по адресу посетителя. Если у домена есть запись AAAA,
после запуска проверяется, какой адрес видит стенд: обращение `curl -6 https://ДОМЕН/`
и последняя строка журнала (`./scripts/compose.sh logs --tail 1 caddy`). Адрес сети
контейнеров вместо адреса посетителя значит, что Docker принял соединение через свой
посредник и все посетители по IPv6 делят один счётчик. Тогда либо в Docker включается
IPv6 (`"ipv6": true` и `"ip6tables": true` в `/etc/docker/daemon.json`), либо запись AAAA
не публикуется.

## 3. Доставка кода

Выкладку выполняет `scripts/deploy.sh` на машине разработчика (Linux, macOS или Git Bash
в Windows; нужны Docker и `ssh`):

```bash
./scripts/deploy.sh --host regionlens@АДРЕС --port 22
```

Сценарий:

1. передаёт на сервер в `/srv/regionlens` описание служб, `Caddyfile`, сценарий роли
   базы (`docker/postgres-init.sh`), сценарии (`scripts/compose.sh`, `deploy.sh`,
   `backup.sh`, `restore.sh`), юниты systemd и `.env.example`;
2. проверяет, что на сервере есть `.env` (при первой выкладке его ещё нет — раздел 4);
3. загружает базовые образы сборки и проверяет из сети Docker доступ к PyPI и зеркалу
   Debian: без него сборка не падает, а висит;
4. собирает образ `regionlens:ВЕРСИЯ-ДАТА` для linux/amd64 из последнего коммита
   (`git archive HEAD`), а не из рабочей папки: файл, которого нет в репозитории, в образ
   не попадёт, незакоммиченная правка — тоже, о ней сценарий предупреждает;
5. передаёт его потоком `docker save | gzip | ssh … docker load` (около 500 МБ в сжатом
   виде); образы Caddy, PostgreSQL и Valkey запрашиваются у реестра при каждой выкладке
   (под тем же ярлыком выходят исправления уязвимостей) и передаются так же, если
   на сервере их нет или они другие: Docker Hub из России доступен не всегда;
6. на сервере — этим же сценарием с ключом `--apply` — снимает резервную копию (если
   база уже работает), ставит на новый образ ярлык `regionlens:latest`, заменяет
   контейнеры, ждёт ответа `/healthz`, проверяет `/readyz`, удаляет образы старше трёх
   последних и напоминает о юнитах systemd, которые изменились или не установлены.

Хост, порт и каталог можно задать переменными `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_DIR`.
`DEPLOY_WORKTREE=1` собирает образ из рабочей папки — для пробного стенда.
Из России часть адресов сети доставки `deb.debian.org` не отвечает, и сборка образа
виснет на загрузке пакетов, поэтому пакеты Debian берутся с зеркала
`http://mirror.yandex.ru`; другое зеркало задаёт `DEPLOY_DEBIAN_MIRROR`, пустое
значение возвращает `deb.debian.org`. Дополнительные ключи `docker build` —
`DEPLOY_BUILD_ARGS`.
Отказ до замены контейнеров оставляет работающую версию. Прежний образ возвращается
ключом `--rollback`; схему базы откат не возвращает — если выкладка её меняла, база
восстанавливается из копии, снятой перед выкладкой (раздел 8).

Все команды compose на сервере — через `scripts/compose.sh`: он подставляет описание
служб, `.env` (без `--env-file` Compose ищет `docker/.env`, `POSTGRES_PASSWORD`
не подставляется, и обрывается даже `logs`) и необязательный `docker/compose.server.yml`
с дополнениями этого сервера (порты, пределы памяти), который выкладка не перезаписывает.

## 4. Окружение

При первой выкладке сценарий остановится на проверке `.env`. На сервере:

```bash
cd /srv/regionlens && cp .env.example .env && chmod 600 .env
```

Обязательно задаются:

| Переменная | Значение |
|---|---|
| `DJANGO_SETTINGS_MODULE` | `config.settings.production` |
| `DJANGO_SECRET_KEY` | случайная строка не короче 50 знаков |
| `DJANGO_DEBUG` | `False` |
| `DJANGO_ALLOWED_HOSTS` | доменное имя стенда |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `https://` и доменное имя |
| `DJANGO_ADMINS` | адрес, на который приходят письма об ошибках 500 и о сбоях сбора и сборки (через запятую, если адресатов несколько) |
| `DOMAIN` | доменное имя для сертификата |
| `ACME_EMAIL` | адрес для уведомлений об истечении сертификата |
| `POSTGRES_PASSWORD` | пароль базы данных; без знаков `@ : / ? #` — он входит в адрес соединения |
| `EMAIL_BACKEND` | `django.core.mail.backends.smtp.EmailBackend` — консольную почту проверка стенда не пропустит |
| `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_SSL` | почтовый узел (раздел 11) |
| `DEFAULT_FROM_EMAIL`, `SERVER_EMAIL` | адрес отправителя писем и писем об ошибках на домене стенда |
| `FIELD_ENCRYPTION_KEYS`, `FIELD_ENCRYPTION_KEY_ID` | ключ AES-256-GCM, которым в базе шифруются ключи кодов входа: `manage.py crypto_keys --field`; без него проверка стенда не пропустит запуск |
| `BACKUP_SIGNING_KEY`, `BACKUP_VERIFY_KEY`, `BACKUP_RECIPIENT_KEY` | ключи шифрования и подписи резервных копий: `manage.py crypto_keys --backup ФАЙЛ` (раздел 8) |

Желательно задать:

| Переменная | Значение |
|---|---|
| `BACKUP_REMOTE` | хранилище rclone для вывоза резервных копий (раздел 8) |
| `SENTRY_DSN` | ключ проекта Sentry — по желанию, в дополнение к письмам об ошибках |
| `DUCKDB_BUILD_MEMORY_LIMIT` | предел памяти сборки склада, по умолчанию `1GB` |
| `WEB_CONCURRENCY` | рабочих процессов gunicorn — по числу ядер сервера, по умолчанию 4: сборка страницы занимает процессор |
| `REQUESTS_PER_MINUTE` | обращений к сайту с одного адреса в минуту, по умолчанию 600; адрес IPv6 считается сетью /64; сверх предела — ответ 429 без сборки страницы; 0 выключает |
| `PUBLIC_MAIL_PER_HOUR` | писем в час по действиям посетителей без входа (регистрация, восстановление пароля) на весь сайт, по умолчанию 120 — ниже суточного предела почтовой службы |
| `ANONYMOUS_BODY_BYTES`, `MEMBER_BODY_BYTES` | предел тела запроса без входа (1 МБ) и после входа (34 МБ); больше принимает только загрузка выпуска набора от того, кто управляет данными |
| `DJANGO_SECRET_KEY_FALLBACKS` | прежние секретные ключи при плановой смене `DJANGO_SECRET_KEY`: открытые сеансы и ссылки из писем действуют до конца срока; через три дня убрать |
| `DATABASE_STATEMENT_TIMEOUT_MS` | предел времени одного запроса к PostgreSQL, по умолчанию 60 000 |
| `USERDATA_*` | пределы своих данных: загрузка 25 МБ, таблица 300 МБ, значений 1 млн, таблиц 20, место 200 МБ, загрузок в час 20, разборов одновременно 2 по 120 с, память разбора 768 МБ, версий таблицы на диске 5, действующих закрытых ссылок на таблицу или исследование 10, неудачных попыток открыть ссылку с адреса за 10 минут 30, исследований 20 по 40 карточек и заметок, правок исследования за 10 минут 300, предпросмотров формулы за 10 минут 120; перечень с пояснениями — в `.env.example` |

`REGIONLENS_IMAGE` остаётся `regionlens:latest`: выкладка переставляет этот ярлык.
Адреса базы данных и Valkey внутри сети контейнеров задаёт `docker/compose.prod.yml`
(`DATABASE_URL`, `VALKEY_URL`); значения из `.env` для них не используются.

**Роль базы.** `POSTGRES_USER` и `POSTGRES_PASSWORD` — роль приложения. При создании
каталога данных её заводит `docker/postgres-init.sh`: роль владеет базой, но прав
суперпользователя у неё нет — запрос, подменённый через уязвимость приложения, не прочитает
файлы сервера базы и не запустит в нём программу. Суперпользователь `postgres` остаётся
без пароля и доступен только изнутри контейнера:
`./scripts/compose.sh exec postgres psql -U postgres`. Стенд, чей том базы создан раньше,
работает как прежде — там роль приложения остаётся суперпользователем. Перевод: копия
(`scripts/backup.sh`), остановка стенда, удаление тома `postgres_data`, запуск
и восстановление (`scripts/restore.sh`, раздел 8).

**Сети.** Прокси и приложение — в сети `edge`, приложение, база и Valkey — в сети
`backend` без выхода наружу: прокси базу не видит, база и Valkey не видят интернет.
Контейнеры работают без привилегий ядра, кроме перечисленных в описании служб, и не могут
их повысить; у прокси и Valkey файловая система только на чтение.

Блок «Безопасность» в `.env.example` заполнен рабочими значениями
(`SECURE_SSL_REDIRECT=True`, `SECURE_HSTS_SECONDS=31536000`, обе куки `Secure`).
Читает эти переменные только `config/settings/production.py`, а compose передаёт
тот же `.env` внутрь контейнера — значение, ослабленное «ради разработки», окажется
в эксплуатации. Точка входа контейнера выполняет
`manage.py check --deploy --fail-level WARNING` и на таких значениях запуск прерывает —
как и без адресатов писем об ошибках (`DJANGO_ADMINS`) или Sentry; сознательное
отступление задаётся `SKIP_DEPLOY_CHECK=1`.

Секретный ключ:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(64))"
```

Файл `.env` не попадает ни в репозиторий, ни в образ: он перечислен в `.gitignore`
и в `.dockerignore`. После заполнения выкладка повторяется с машины разработчика
(раздел 3).

## 5. Запуск

Службы запускает выкладка. Вручную — тот же `compose.sh`:

```bash
./scripts/compose.sh up -d
```

Точка входа контейнера `web` выполняет: проверку настроек развёртывания, сборку статики,
миграции и загрузку справочника территорий. Сборка статики повторяется при каждом
запуске: каталог подключён именованным томом, а том заполняется содержимым образа
только пока пуст — со второй выкладки прокси отдавал бы файлы прежней версии. Имена
файлов несут отпечаток содержимого, поэтому промах дал бы страницу вовсе без стилей.

## 6. Первоначальное наполнение

Сборка аналитического склада — от одной до трёх минут, в контейнере приложения:

```bash
./scripts/compose.sh exec web python manage.py etl_build --full
```

Тексты методики и глоссария и английские названия справочника:

```bash
./scripts/compose.sh exec web sh -c "python manage.py seed_content && python manage.py seed_content_en && python manage.py seed_catalog_names"
```

Учётная запись администратора:

```bash
./scripts/compose.sh exec web python manage.py createsuperuser
```

Панель управления открывается только после входа с одноразовым кодом: при первом
переходе в неё администратор включает его в кабинете («Настройки» → «Включить вход
с кодом») приложением-генератором на телефоне и сохраняет резервные коды. Остальным
ролям назначает «Администратор» флажками в разделе «Пользователи и роли». Если телефон
и резервные коды потерял единственный администратор, вход с кодом выключается командой:

```bash
./scripts/compose.sh exec web python manage.py reset_two_factor admin@example.ru
```

Новую версию набора ежедневный сбор источников (`collect --due`) находит на странице
«Если быть точным», скачивает и проверяет: собирает склад рядом с рабочим и сравнивает
с ним. Администратору приходит письмо с главным из отчёта — сколько рядов добавлено,
исчезло и переименовано, сколько значений изменилось, сменились ли единицы и связи
с выпусками источников, какие появились методические примечания, на какие пропавшие
ряды ссылаются справочники. Версию принимают или отклоняют в карточке проверки
(«Загрузка данных»); принятая собирается в рабочий склад отдельным процессом, сайт
работает на прежних данных, пока новый склад не собран целиком. Набор можно загрузить
и вручную («Загрузка данных» → «Новый выпуск набора») — он проходит ту же проверку.

### Выпуски источников

Ряды, которые продолжаются по изданиям Росстата, и ряды Банка России и ФНС собирает
команда `collect`: она находит новый выпуск, кладёт его в архив (том `archive`, опись
`MANIFEST.csv`), разбирает (том `sources`) и пересобирает склад. Первый сбор берёт
последние выпуски бюллетеня и таблицы ВРП, если Росстат их публикует, снимок сервиса
данных Банка России (пять запросов по всей истории с 2019 года) и все даты реестра МСП
ФНС — 122 запроса, около получаса при обрывах рукопожатия:

```bash
./scripts/compose.sh exec web python manage.py collect --all
```

Выпуск, который сайт источника не отдаёт, сбор не получит. На 08.11.2026 файлы Росстата
отвечают сборщику 404: и бюллетень (страница перечисляет только выпуск за январь 2026 года,
прежние адреса `info-stat-ММ-ГГГГ` не открываются), и таблица ВРП, хотя ссылка на неё
на странице есть. Поэтому выпуски Росстата при первом наполнении
берутся из архива машины разработчика (`data/archive/`): каталоги копируются в контейнер
и регистрируются по одному, склад пересобирается после последнего (выпуски в RAR
распаковывает bsdtar из образа):

```bash
tar -cf - -C data/archive rosstat_bulletin rosstat_grp | ssh ПОЛЬЗОВАТЕЛЬ@СЕРВЕР "docker exec -i regionlens-web tar -xf - -C /tmp"
ssh ПОЛЬЗОВАТЕЛЬ@СЕРВЕР 'docker exec regionlens-web sh -c "for f in /tmp/rosstat_bulletin/*; do python manage.py collect rosstat_bulletin --file \$f --no-build; done; python manage.py collect rosstat_grp --file /tmp/rosstat_grp/*.xlsx"'
```

Выпуск, который ещё лежит на сайте, добавляется по адресу: `collect rosstat_bulletin --url АДРЕС`.

Сайты Росстата подписаны корнем НУЦ Минцифры; сборщик доверяет ему по файлу
`data/reference/certs/russian_trusted_ca.crt`, только для своих запросов. Запросы идут
мимо прокси из окружения. Росстат, Банк России (`www.cbr.ru`) и ФНС (`rmsp.nalog.ru`)
отвечают не всем зарубежным адресам — доступ к каждому проверяется с сервера до включения
таймера.

### Таймеры

Сбор источников (ежедневно, 07:00 по Москве), статистика посещений (ежечасно),
резервная копия (ежедневно, 03:30) и удаление персональных данных по сроку из политики
обработки (ежедневно, 04:15, `manage.py prune_personal_data`: сеансы, попытки входа,
сведения обращений, таблицы без владельца с истёкшим сроком и осиротевшие файлы своих таблиц;
занятый процессом файл удаляется при следующем запуске) — таймеры хоста: они работают и тогда, когда
приложение упало, и не требуют очереди задач. Юниты ставятся один раз и после
изменений, о которых напоминает выкладка:

```bash
sudo cp /srv/regionlens/deploy/systemd/regionlens-* /etc/systemd/system/ && sudo systemctl daemon-reload
```

```bash
sudo systemctl enable --now regionlens-collect.timer regionlens-visits.timer regionlens-backup.timer regionlens-prune.timer
```

Исход сбора виден в панели: «Источники» (журнал выпусков, сверка рядов с набором,
«Собрать сейчас») и «Состояние служб» → «Сбор источников»; выпуск, который не удалось
разобрать, попадает в «Требует внимания», а склад остаётся прежним. Тот же ежедневный
сбор раз в сутки сверяет версию набора на странице «Если быть точным» с загруженной
(«Состояние служб» → «Версия набора»); вышедшая новая версия — пункт «Требует внимания»,
загружается она вручную в «Загрузке данных». После сборки склада ряды с пометкой
«публикация прекращена», у которых появились значения, попадают в замечания качества.

### Свои данные

Таблицы пользователей лежат в томе `userdata` (`/app/data/userdata`): исходный файл,
распакованная таблица и файл DuckDB набора. Большие таблицы разбирает служба
`userdata-worker` (`manage.py userdata_worker`): сайт кладёт заявку в каталог `.jobs` тома,
служба запускает `manage.py userdata_build` отдельным процессом, не больше двух
одновременно и не дольше двух минут; память DuckDB одного разбора — `USERDATA_PARSE_MEMORY`.
Остановка службы ждёт начатый разбор до 150 с; журнал — `logs -f userdata-worker`, отметка
жизни — файл `.jobs/heartbeat`, по ней служба считается здоровой. Очередь в копию
не входит. Caddy
пропускает к адресам загрузки таблицы и её новой версии (`/<язык>/own-data/new/`,
`/<язык>/own-data/<таблица>/versions/new/`) запрос до 32 МБ, чтобы о файле больше
25 МБ сказало приложение, а не оборванное соединение; остальные запросы — до 25 МБ.
Закрытые ссылки `/s/<токен>` — без языка; `robots.txt` закрывает их от поисковиков.
Сбой разбора, не объяснённый правилами, приходит письмом администратору без содержимого
файла; в «Состоянии служб» — число таблиц, место и разборы за сутки.

### Статистика посещений

Счётчиков на страницах нет: Caddy пишет журнал обращений в JSON (том `caddy_logs`,
части по 20 МБ, 30 суток), а команда `visits` раз в час дописывает его новые строки
в помесячную историю (том `visits`) — без последней части адреса, строки запроса
и служебных меток в адресах, без статики и проверок состояния. По истории GoAccess
из образа заново считает отчёт; обходчики поисковых систем не считаются. История
переживает удаление старых частей журнала и входит в резервную копию. Раздел панели «Посещения» показывает посетителей
по дням и месяцам, страницы, переходы с других сайтов, ответы 404, системы и браузеры;
посетители по дням выгружаются в CSV. Вручную:

```bash
./scripts/compose.sh exec web python manage.py visits
```

## 8. Обновление и резервные копии

С машины разработчика:

```bash
./scripts/deploy.sh --host regionlens@АДРЕС
```

С пересборкой аналитического склада (при выходе новой версии набора):

```bash
./scripts/deploy.sh --host regionlens@АДРЕС --with-etl
```

Справочник территорий загружается при каждом запуске контейнера. Если в выкладке
правились английские версии методики и глоссария или названия справочника, после неё
они загружаются заново:

```bash
./scripts/compose.sh exec web sh -c "python manage.py seed_content_en && python manage.py seed_catalog_names"
```

Русские тексты методики и глоссария `seed_content` обновляет только с `--force`, и тогда
правки, сделанные в панели, перезаписываются. Переводы примечаний Росстата проставляет
сборка склада: их правка выкладывается с `--with-etl`.

Возврат прежнего образа:

```bash
./scripts/deploy.sh --host regionlens@АДРЕС --rollback
```

### Резервные копии

Копию снимает таймер хоста (`scripts/backup.sh`), а не приложение: она нужна и тогда,
когда контейнеры упали. Копируются база PostgreSQL, загруженные выпуски набора, архив
выпусков источников, история посещений и свои таблицы учётных записей (том `userdata`);
склад и разобранные выпуски воспроизводятся из них и не копируются. Копии старше 14 суток удаляются
(`BACKUP_RETENTION_DAYS`).

Копия на том же диске не спасает от потери сервера, поэтому свежие файлы вывозятся
через [rclone](https://rclone.org) в объектное хранилище S3 — например, Selectel.
Ключи доступа хранятся в настройках rclone пользователя `regionlens`, а не в `.env`:
тот попадает и в контейнеры. Адрес и регион берутся из панели Selectel («Объектное
хранилище» → «Доступ по S3»), ключи — у сервисного пользователя с доступом к контейнеру
хранилища. Копия содержит хэши паролей и ключи кодов входа, поэтому контейнер
хранилища закрытый (`acl=private`), а сервисный пользователь видит только его. От имени
`regionlens`:

```bash
rclone config create selectel s3 provider=Other endpoint=s3.ru-1.storage.selcloud.ru region=ru-1 access_key_id=КЛЮЧ secret_access_key=СЕКРЕТ acl=private
```

```bash
echo "BACKUP_REMOTE=selectel:regionlens-backups" >> /srv/regionlens/.env
```

Во внешнем хранилище копии старше 30 суток удаляются (`BACKUP_REMOTE_RETENTION_DAYS`,
0 — хранить все). Проверка — ручной запуск копии и перечень файлов хранилища:

```bash
/srv/regionlens/scripts/backup.sh && rclone ls selectel:regionlens-backups
```

Старые копии из хранилища удаляет сам сервер, значит, тот, кто получил сервер, может
стереть и их. Если хранилище поддерживает версии объектов, они включаются для контейнера
копий: удалённое сервером остаётся прежней версией, а срок версий задаёт правило
хранилища, не сервер.

В конце каждой копии сценарий оставляет отметку (`manage.py record_backup`): в панели
видно время, размер и вывезена ли копия; копия старше полутора суток подсвечивается.

**Шифрование и подпись копий.** Перед вывозом файлы копии шифруются
(`manage.py backup_seal`): на каждый файл — одноразовая пара X25519, общий секрет
с открытым ключом получателя через HKDF-SHA256 даёт ключ AES-256-GCM. Открытые файлы
удаляются, рядом кладётся опись `manifest-ОТМЕТКА.json` (размер и SHA-256 каждого файла)
и её подпись Ed25519 `manifest-ОТМЕТКА.sig`. На сервере лежит только открытый ключ
получателя: сервер копию шифрует, но прочитать не может. Закрытый ключ расшифровки
выпускается один раз и уносится с сервера:

```bash
./scripts/compose.sh run --rm --no-deps --volume "$HOME:/out" web python manage.py crypto_keys --field --backup /out/backup.key
```

Строки `FIELD_ENCRYPTION_*` и `BACKUP_*` из вывода — в `.env`, файл `~/backup.key`
— в менеджер паролей или на носитель администратора, затем удалить с сервера. Вместе
с ним вне сервера хранится и копия строки `FIELD_ENCRYPTION_KEYS`: без неё ключи кодов
входа из восстановленной базы не прочитать.

Смена ключа кодов входа: новый ключ (`crypto_keys --field`) дописывается в
`FIELD_ENCRYPTION_KEYS` первым и называется в `FIELD_ENCRYPTION_KEY_ID`, после
перезапуска — `manage.py reencrypt_secrets`, затем прежний ключ убирается.

Восстановление базы — `./scripts/restore.sh backups/db-ОТМЕТКА.dump`, базы,
загруженных наборов, архива выпусков, статистики посещений и своих таблиц —
`./scripts/restore.sh --all ОТМЕТКА` (архив разбирается заново, склад пересобирается,
записи таблиц без файлов убирает `prune_personal_data`);
проверка копии без восстановления — ключ `--check`. Зашифрованная копия
восстанавливается по отметке с закрытым ключом: `./scripts/restore.sh --all ОТМЕТКА
--key ~/backup.key`; сначала проверяются подпись описи и SHA-256 файлов, подменённая
копия не расшифровывается, расшифрованное удаляется по окончании. `--check ОТМЕТКА`
без ключа проверяет подпись и суммы, с ключом — ещё и оглавление выгрузки. Копию
из внешнего хранилища сначала возвращают на сервер: `rclone copy
selectel:regionlens-backups/ backups/ --include "*-ОТМЕТКА.*"`. `.env` в копию не входит:
на новом сервере он заполняется заново. С другим `DJANGO_SECRET_KEY` восстановление
работает — перестают действовать только открытые сеансы и неиспользованные ссылки
из писем; `FIELD_ENCRYPTION_KEYS` нужен прежний, иначе вход с кодом придётся
выключить (`manage.py reset_two_factor`) и включить заново.

## 9. Порт 443 занят другой службой

Если на сервере уже работает VPN или иная служба на стандартном порту:

**Нестандартный порт.** В `.env` задаётся `HTTPS_PORT=8443`; адрес стенда —
`https://ДОМЕН:8443`. Самый простой способ; недостаток — порт в адресе.

**Второй адрес IPv4.** Если провайдер выделяет дополнительный адрес, Caddy
привязывается к нему, а прежняя служба остаётся на основном.

**Разделение по имени.** Если занимающая порт служба сама является обратным прокси,
она направляет обращения к домену RegionLens на порт приложения; стандартный порт
сохраняется.

## 10. Что делать при неудаче

| Признак | Причина | Действие |
|---|---|---|
| Контейнер `web` перезапускается | Не задан `DJANGO_SECRET_KEY`, недоступна база или не пройдена проверка настроек (в том числе без `DJANGO_ADMINS` и `SENTRY_DSN`) | `./scripts/compose.sh logs web` |
| Выкладка остановилась на «Нет .env» | Первая выкладка | Раздел 4, затем выкладка ещё раз |
| Выкладка упала после замены контейнеров | Новая версия не отвечает | `./scripts/deploy.sh --rollback`; при изменённой схеме — `restore.sh` из копии перед выкладкой |
| `readyz` сообщает об отсутствии склада | Не выполнена сборка | `etl_build --full` |
| `readyz` сообщает о пустом справочнике | Справочник территорий не загрузился | `seed_reference` |
| Caddy не получает сертификат | Домен не указывает на сервер либо закрыт порт 80 | Проверить запись DNS и правила экрана |
| Документ не скачивается, ответ 400 | Склад не собран или у ряда нет данных | Текст ответа называет причину |
| Нехватка памяти при сборке склада | Предел сборки выше доступной памяти | Уменьшить `DUCKDB_BUILD_MEMORY_LIMIT` |
| Сборка из панели «Запускается» дольше минуты | Процесс сборки не стартовал или остановлен | `./scripts/compose.sh logs web`; сборка без исхода 30 минут закрывается сама |
| Ответ на обращение «Не доставлено» | Почтовый узел отказал | Причина — в карточке; после исправления — «Отправить ещё раз» |
| Письма уходят в спам | Нет записей SPF, DKIM, DMARC | Раздел 11 |
| «Посещения» пусты или «Статистика посещений» красная | Таймер `regionlens-visits` не установлен или журнала Caddy ещё нет | `systemctl status regionlens-visits.timer`; `./scripts/compose.sh exec web python manage.py visits` |
| Копия «только на сервере» | Не задан `BACKUP_REMOTE` или rclone не настроен | Раздел 8 |
| Страницы открываются, но медленно | Недоступен Valkey | `./scripts/compose.sh logs valkey`; сайт работает и без кэша |
| Ответ 429 «Слишком много запросов» | С адреса больше `REQUESTS_PER_MINUTE` обращений в минуту: за общим адресом много людей или идёт обход сайта | Поднять предел в `.env` и перезапустить `web` |
| Ответ 413 при отправке формы или файла | Тело запроса больше предела отправителя | Раздел 4, `ANONYMOUS_BODY_BYTES` и `MEMBER_BODY_BYTES`; таблицы загружают после входа |
| Ответ 503 сразу, без ожидания | Приложение занято: прокси не копит запросы сверх 64 одновременных | Нагрузка в «Посещениях»; при свободных ядрах — поднять `WEB_CONCURRENCY` |

## 11. Почтовый домен

Ответы на обращения, извещения администраторов о новых обращениях, письма об ошибках
и восстановление пароля уходят письмами. Письмо от домена без подтверждения подлинности
почтовые службы отправляют в спам или отвергают, поэтому у домена отправителя
(`DEFAULT_FROM_EMAIL`) настраиваются три записи DNS. Значения выдаёт почтовая служба
(почта Selectel, Яндекс 360 для домена и другие); на VDS Selectel порт 25 закрыт —
отправка идёт через порт 465. Здесь — вид записей:

| Запись | Имя | Значение (пример) | Зачем |
|---|---|---|---|
| TXT (SPF) | `@` | `v=spf1 include:_spf.yandex.net -all` | какие узлы вправе отправлять письма домена |
| TXT (DKIM) | `mail._domainkey` | `v=DKIM1; k=rsa; p=…` | подпись письма ключом домена |
| TXT (DMARC) | `_dmarc` | `v=DMARC1; p=quarantine; rua=mailto:ВЛАДЕЛЕЦ@ДОМЕН` | что делать с письмом, не прошедшим проверку, и куда слать отчёты |

Проверка — отправить письмо на адрес Gmail и открыть «Показать оригинал»: SPF, DKIM
и DMARC должны быть `PASS`. Ожидание почтового узла — не дольше 10 секунд; исход
последней отправки виден в «Состоянии служб».

## 12. Наблюдение

Сервер не может сообщить о собственном падении, поэтому доступность проверяется
снаружи, а ошибки — письмами:

* **ошибки** — письмо адресатам из `DJANGO_ADMINS` с трассировкой и сведениями
  о запросе; одна и та же ошибка (вид исключения и место в коде) — не чаще раза в час,
  чтобы сбой под нагрузкой не засыпал почту. По желанию — ещё и Sentry (`SENTRY_DSN`),
  без персональных данных (`send_default_pii=False`);
* **сбор и сборка** — письмо тем же адресатам, если выпуск источника не разобран (обычно
  источник сменил вид таблицы), источник не ответил две проверки подряд или сборка склада
  по таймеру не удалась; одно и то же событие — не чаще раза в неделю;
* **доступность** — любой внешний монитор адреса (UptimeRobot и подобные), проверяющий
  `https://ДОМЕН/healthz` раз в пять минут;
* **посещения** — раздел панели «Посещения» (раздел 6).

## 13. Персональные данные: что сделать до открытия

Сайт с регистрацией и формой обращения обрабатывает персональные данные, и его владелец —
оператор по 152-ФЗ. Текст политики, согласие и сроки хранения сайт показывает сам
(`/privacy/`, `/consent/`); остальное делает оператор:

* **уведомление Роскомнадзора** — до начала обработки (ч. 1 ст. 22 152-ФЗ): адрес
  оператора, цели и состав данных — как в `/privacy/`, дата начала — день открытия;
* **данные в России** — сервер и хранилище копий (`BACKUP_REMOTE`) в российском центре
  обработки данных (ч. 5 ст. 18); ненулевой `BACKUP_REMOTE_RETENTION_DAYS`, иначе
  политика назовёт срок хранения копий «без срока»;
* **Sentry** — служба за рубежом: без `SENTRY_DSN` ошибки приходят только письмами;
  с ним — с учётом ст. 12 о трансграничной передаче;
* **уровень защищённости и перечень лиц** — решение оператора о типе актуальных угроз
  и документ с перечнем лиц, у которых есть доступ к данным (пп. 7 и 13 «в» Требований,
  утверждённых постановлением Правительства РФ от 01.11.2012 № 1119); расчёт уровня —
  в разделе «Защита персональных данных» [ARCHITECTURE.md](ARCHITECTURE.md);
* **очистка по срокам** — таймер `regionlens-prune` включён (раздел 6, «Таймеры»).

## 14. Если сервер взломан

Признаки: незнакомые процессы или контейнеры, вход по SSH с чужого адреса
(`journalctl -u ssh`), правки файлов стенда, письма об ошибках с незнакомыми запросами.
Адрес для сообщений об уязвимостях сайт публикует в `/.well-known/security.txt`.

1. **Закрыть доступ.** Остановить прокси (`./scripts/compose.sh stop caddy`) или закрыть
   порты 80 и 443 экраном. Снять снимок диска в панели провайдера: он нужен для разбора.
2. **Не чинить взломанный сервер.** Стенд разворачивается на новом сервере (разделы 2–6)
   из копии, снятой до взлома (`restore.sh --all`, раздел 8). Закрытый ключ копий
   на сервере не хранится: вывезенные копии взломщик прочитать не мог.
3. **Сменить секреты.** `DJANGO_SECRET_KEY` — без `DJANGO_SECRET_KEY_FALLBACKS`: все сеансы
   и ссылки из писем перестают действовать. `POSTGRES_PASSWORD`, пароль почтового узла,
   ключи хранилища копий (rclone), ключи SSH, `BACKUP_*`. `FIELD_ENCRYPTION_KEYS` — новый
   ключ и `manage.py reencrypt_secrets` (раздел 8).
4. **Сообщить.** Если затронуты персональные данные (база, копии, журнал), оператор
   уведомляет Роскомнадзор в течение 24 часов с момента обнаружения, а о результатах
   внутреннего расследования — в течение 72 часов (ч. 3.1 ст. 21 152-ФЗ). Пользователям
   — письмо с просьбой сменить пароль: в базе хранятся только хэши паролей, но подбор
   по утёкшим хэшам возможен.
5. **Найти вход.** Журнал Caddy и SSH на снимке диска, версии образов, дата последних
   обновлений. Пока путь взлома не найден, новый стенд открыт той же уязвимости.
